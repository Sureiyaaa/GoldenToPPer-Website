# Project creation diagnosis and regression checks

Verified on 2026-10-07 against the Supabase project configured in `.env.local`.
No credentials are included here.

## Confirmed cause and ownership

The live catalog result supplied from Supabase SQL Editor confirms an enabled
`on_project_created` trigger (`tgenabled = O`):

```sql
CREATE TRIGGER on_project_created
AFTER INSERT ON public.project_table
FOR EACH ROW EXECUTE FUNCTION auto_insert_navbar_project();
```

`public.auto_insert_navbar_project()` is a PL/pgSQL `SECURITY DEFINER` trigger
function. It inserts a navigation row within the project insertion transaction:

| Column | Trigger value |
| --- | --- |
| `project_id` | `NEW.id` |
| `nav_title` | `NEW.title` |
| `nav_image_url` | `/images/placeholder.webp` |
| `tagline` | `Discover our newest development.` |
| `display_order` | `COALESCE(MAX(display_order), 0) + 1` |
| `is_active` | `NEW.is_active` |

`navbar_projects.id` is generated by an identity column. Its other columns have
no column defaults. `project_table.id` uses `project_table_id_seq`; the basic
creation action never supplies either table's generated ID.

Before this fix, `createBasicProjectAction()` inserted a second navigation row
after the trigger had already created one. The verified
`navbar_projects_project_id_unique` constraint correctly rejected that insert.

The enabled trigger remains authoritative for new navigation rows. There is no
repository evidence that it is obsolete. Basic creation now reads by
`project_id` with `single()`, requiring exactly one row, and updates that same
row. It keeps the trigger's order and initializes the app's existing values:
the submitted title, empty tagline, null navigation logo, and `is_active: true`
as the saved navigation preference. No navigation insert or upsert is performed
by basic creation. A missing row causes a controlled error and cleanup, without
sleeping, retrying, or calling the global ensure helper.

Public visibility still requires an active navigation preference, an active
project, and an unarchived project. New projects explicitly start
`project_table.is_active = false`, so a saved navigation preference of true does
not publish them.

## Cleanup and errors

The verified `navbar_projects_project_id_fkey` uses `ON DELETE CASCADE`, so its
navigation row cannot block deletion of a failed newly created project.
`inquire` and `loan_preapp` have restrictive project references. Other inspected
references use cascade or set-null behavior.

If navigation setup fails, the action logs the technical error and deletes only
the newly inserted project. A successful delete cascades to its navigation row.
If deletion fails, the action attempts to archive the incomplete project and
keep it Hidden, releasing its slug from active-project uniqueness checks. The
admin receives a controlled message explaining that it was archived. If that
fallback also fails, the message identifies the project ID for recovery in
Projects. Each technical failure is logged server-side.

Expected authentication, validation, and duplicate-slug messages remain
friendly. Unexpected database errors use a generic message. The UI and its
error styling were unchanged. No transaction/RPC redesign, migration, trigger
change, or constraint change was needed.

## Validation

`node --test tests/*.test.cjs` passed all 40 tests, including 13 new project
regression tests. The new tests model the supplied trigger definition and
exercise the actual exported actions with a database mock. They also execute
the actual page creation callback to check the single creation call, audit
ordering, redirect, and controlled failures. Failure cases cover missing or
multiple navigation rows, lookup/update errors, an update matching no rows,
transport errors, cascade cleanup, failed delete with archive fallback, and
failed delete plus failed archive.

Live checks used the real server actions and Supabase clients, with an
authenticated-session stub because the actions were invoked outside Next.js.
Public queries used the configured anonymous client. They did not test browser
login or render the editor.

Both test projects were archived and Hidden after the checks. Their navigation
rows were retained and disabled, consistent with normal archive behavior.

The production build passed. `next.config.ts` already disables build-time type
validation, so a successful build does not establish a passing typecheck.
Separate typecheck and lint commands remain blocked by pre-existing dependency
issues: TypeScript cannot resolve the stub `@types/mapbox__point-geometry`
package, and ESLint cannot import `eslint-config-next/core-web-vitals` from the
installed `eslint-config-next@0.2.4` package. These also failed before this fix.

After deploying the application change, verify creation from an authenticated
admin browser, its real audit entry, the editor redirect, and the existing
Navigation Setup presentation. Repeat the catalog check if production uses a
different Supabase database from the one tested here. The trigger's existing
`MAX(display_order) + 1` calculation can give simultaneous creations the same
order; this fix preserves that behavior without redesigning ordering.
